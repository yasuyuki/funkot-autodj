## なぜやっているか

`analysis.rs` の区間長判定は手調整の if カスケードで、閾値が Shirube / IVY / Starmine /
Love & Joy / Sakura / Totsumal といった**個別曲に合わせて刻まれている**。10曲規模の過学習で、
分岐を1つ足すと別の曲が壊れる。

根本原因は特徴量が**すべて広帯域エネルギー**（RMS / mid / hf / midhigh_ratio /
ZCR centroid）で、Funkot のイントロ・アウトロを実際に定義している
「旋律・ボーカルが無く機械リズムが反復する」性質を測る特徴が1つも無いこと。
加えて**実音源の正解ラベルも精度指標も存在せず、改善したかを測れなかった**。

方針（ユーザー確認済み）:

1. 正解ラベルは半自動アノテーション CLI で作る（最良値＋許容集合。曖昧な曲があるため）
2. 判定は候補スコアリング＋オフライン学習した重み（実行時 ML 依存ゼロ、決定的）
3. `outro_bars` は「構造境界」と「mix リード」を分離する

### 着手前チェックの結果（2026-08-02、実音源14曲）

測定は `section_diag --new-features`。**3項とも「そのまま学習に入れてはいけない」側の答え**
が出た。共通の病根は「スケールの違う生の次元をそのまま距離・類似度に入れている」こと。

#### 0. 先に潰したもの: 窓外バーのゼロ詰めが構造計算に混ざっていた

`features::bar_features` は**窓の外のバーに全ゼロの `BarFeatures::default()` を返す**仕様。
`diagnose_section_bars_ext` は bar 列を曲全体（約194小節）に取るのに新特徴は
先頭/末尾110秒（`SEGMENT_SECS`）からしか作らないので、**83小節目以降が全ゼロ**のまま
`structure::compute` へ流れていた。結果、全曲の bar 78〜88 に同一形状の偽の novelty ピーク
（band_n8 が 0.56→3.98→0.56 の対称三角）が立ち、それ以降 `mahal` が 138.79 の定数になる。
曲が違うのに同じ値が出るのが見分け方。

**窓に完全に収まる先頭からの連続バーだけを渡すように直した。** 判定は必ず
「バーの位置と窓の範囲」で行う — **特徴量が全ゼロかどうかで判定してはいけない**
（本当に無音の小節を落とすことになる）。`SectionDiag::intro_covered` / `outro_covered`。

`analyze()` は Stage 2 特徴を読まないので実害は診断だけだったが、**Stage 3 はまさに
この配列を学習入力にする段**なので、ここで直しておかないと全曲に同じ偽の境界を学習する。

#### 1. band novelty は実音源でほぼ死んでいる → SSM 前に次元ごと z-score

覆われたバー2058本の分布:

| 列 | mean | max | <0.005 の割合 |
|---|---|---|---|
| chroma_n8 | 0.0146 | 0.183 | 32.8% |
| **band_n8** | **0.0043** | 0.679 | **91.8%** |
| rhythm_n8 | 0.0596 | 0.774 | 10.9% |

band だけ chroma の 1/3・rhythm の 1/14 で、9割以上のバーがゼロ。予想どおり、
生 dB ベクトルのコサインは共通オフセットで 1 付近に張り付く。**入れるなら z-score が要る。**

#### 2. prefix-Mahalanobis を支配しているのは dB 次元ではなく chroma

寄与率（各バーで `diff²/var` を21次元合計で割り、バー方向に平均。14曲平均）:

| side | band_db（7次元） | chroma（12次元） | tonality | voiced |
|---|---|---|---|---|
| INTRO | 0.338 | **0.623** | 0.019 | 0.021 |
| OUTRO | 0.145 | **0.781** | 0.047 | 0.027 |

**当初の懸念（ほぼ一定の dB 次元を 1 dB の変化が支配する）は外れ。** 逆で、dB 次元の
prefix 分散は 0.005〜1350 と大きく、支配しているのは値が 0.03〜0.2 で分散が
1e-7〜1e-3 しかない chroma。prefix は**8小節しか使わない**ので、たまたまその8小節で
一定だった chroma ビンが以後の全バーの距離を決める。`1e-6` フロアが実際に効いた次元は
588次元中21件あり、**フロアだけが歯止めになっている次元が現に存在する**。

対応は絶対値フロアの調整ではなく、**次元ごとの事前標準化**（片側全体、または頑健なスケール）。
1と同じ処方であることに注意。

#### 3. periodicity は現状のままでよい

`features.rs` の自己相関は確かに零詰め無しの循環（`IFFT(|FFT(x)|²)`、2048点、
探索ラグは 44〜294サンプル）。ただし **`periodicity` は `voiced_frac` の二値判定
（閾値 0.35）にしか使われていない**ので、連続値として学習特徴に入れない限り手を入れる必要はない。
入れるときに零詰め版へ直すこと。

#### 4. アウトロの候補集合に 48 が無い（2026-08-04 追記、17曲ラベルから判明）

上の3項は特徴量のスケールしか見ておらず、**候補が正解に届くかを誰も確認していなかった**。

```rust
const SNAP_CANDIDATES: [u32; 4] = [8, 16, 32, 64];        // アウトロ
const INTRO_SNAP_CANDIDATES: [u32; 5] = [8, 16, 32, 48, 64];  // イントロ（48 がある）
```

`pick_by_candidate_scores_outro` は `SNAP_CANDIDATES` をループするだけなので、
**アウトロ側は 48 を仮説として一度も評価しない**。ベースラインの「48 の予測が0回」は
推定器の偏りではなく構造的な不可能である。

**前提だった「ラベルの 48 が正しいか」は 8-04 に耳で確かめ、根拠は残った。**
真値 48 の4曲を新しい境界の定義で聴き直したところ、2曲（Sekaiichi / Love & Joy）は
48 のまま、2曲（Totsumal / Eternal Light）は **64 へ動いた**（32 ではない＝誤差は
広がった）。一方で対照の Monitoring Db が 48 へ動いたので、**真値 48 は3曲**。
13曲ベースラインでは OUTRO の DJ 重大度コスト 16.0 のうち **8.0（50%）**がここから出る
（17曲時点は 36%）。

Stage 3 は「候補 φ(c) + softmax」なので、**候補列挙がこのままだと学習しても
この3曲は原理的に当たらない**。本体に入る前に候補集合を直すこと。

なお `SNAP_TOLERANCE` は 0.25 なので raw≈48 は 64 へ吸われる（32 ではない）。
真値 48 の曲が 32 と予測されているのは snap ではなく**検出器自体が手前で
止まっている**ためで、配列に 48 を足すだけでは直らない可能性がある。**まず raw を見ること。**

（`analysis::outro_trigger_bars`、`CACHE_VERSION` 9→10）。

構造境界の16小節手前でトリガを引けば**つなぎ終えた時点がちょうどアウトロの開始点**になる。
リードが落ちるとトリガ＝構造境界になり、**遷移全体がアウトロの中で起きる** — 一番やっては
いけない場所。実測で作業キャッシュ34曲中3曲（構造境界64小節の曲）がこれに該当していた。

旧実装のリードが条件付きだった理由は「アウトロ解析窓がリード分をカバーしていること」
（`feats.len() >= bars + LEAD + AFTER_WIN`）と `FALLBACK_BARS` クランプだが、
**どちらもトリガの正しさとは無関係**。リードは構造境界に対する算術であって、
解析窓が覆っている必要はない。唯一の実制約は曲の長さで、
`outro_trigger_bars` は「イントロを食い込まない」「構造境界より手前にしない」だけを守る。

トリガ集合は **{24, 32, 48, 80}**（構造境界 {8,16,32,64} + 16）。README 3言語も更新済み。

残り: ラベリング時に `set_manual_bars` へアウトロも書けるようにする（現在はイントロのみ。
アウトロを書くと +16 を推測することになる、という制約が上のルール確定で消えた）。

  クリッピング（peak 1.71）も、合成音源のテストは全部通っていた。実音源に近い密で大音量の
  合成信号をテストに使うこと

### 曲中の減速がテンポ推定窓に入る（2026-08-04、未検証）

**Funkot には曲の途中で減速する曲が多い**（→ [labeling.md](labeling.md)
「『音が減る』は曲中に何度も起きる」）。`KazuyaP - Monitoring Db` は
`イントロ → 音が減る → 減速 → 歌 → 歌が終わる → 加速 → シンセフレーズ → アウトロ`。

デコイとしては解析器に無害である。`analysis.rs` の前提は
**"Mid-song material is never inspected"** で、イントロ格子は曲頭から、アウトロ格子は
曲尾から独立に張るため、曲中の「音が減る」1回目は走査対象に入らない。

**無害でないのはテンポのほう。** BPM は先頭/末尾の**各110秒**をコムフィルタ
（172–188 BPM、0.05刻み）で推定する。180BPM では 1小節 ≈ 1.333秒なので
**110秒 ≈ 82小節 ≈ `MAX_SCAN_BARS_OUTRO`（80）**。つまり**末尾80小節の中で
テンポが変わると、それは推定窓の中で起きている**。Monitoring Db の「加速」が
末尾 64〜32小節あたりなら、まさにこれに当たる。

未検証だが、これで説明が付きうるものが2つある:

- **アウトロの誤りが8件すべて過小**（pred < true）。窓の中にテンポ勾配があると
  コムは折衷値を返し、そこから張った格子で境界コントラストを測ることになる。
  格子がずれれば差が鈍り、検出器は手前で止まる——`analysis.rs` の
  「longer scans shift the full-drop hit」と同じ向きの失敗
- **`Kamurogiku` のアウトロ格子が丸ごと半拍ずれる件**（HANDOFF「次にやること」4）。
  refit が「直すものの無いところに誤差を入れている」のは、
  窓の中の実テンポが一定でないからかもしれない

**確かめ方**: `DECEL:` が溜まったら、`DECEL:yes` の曲と OUTRO の誤り・
`Kamurogiku` 型の位相破綻が相関するかを見る。相関するなら、末尾窓を減速の手前で
打ち切るか、窓内でテンポ一定性を検定して低信頼を立てる。**先に `DECEL:` を集めること**
——いま n=1 で、この状態で設計すると1曲に合わせた大域規則になる。

**`grid-suspicious` は0件だが反証にならない。** 判定は BPM が [172,188] を外れるか
イントロ/アウトロの drift >= 1小節かで、**減速して元のテンポへ戻る曲は差し引き 0 に
見える**。
