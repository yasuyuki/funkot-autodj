## 3. 統合前レビューで見つかった主な問題

### 3.1 アーキテクチャ評価（統合前・統合後とも概ね維持）

良い点:
- `funkot-core`（解析・ミックス・C ABI）と `funkot-cli`（cpal・キー・WAV）の分離が明確
- Pull 型 2デッキ。ローダーが decode → analyze → stretch をオフラインで済ませ、`render` は事前レンダリング済みバッファの合成
- T0（次曲 intro end）逆算の遷移、HPF バススワップ、fade ペアが一貫
- フェード端点の bit-exact テスト、Android 実機制約、失敗履歴のドキュメント化

### 3.2 P0（統合前）

**nav 遷移が realtime audio callback で位相アラインを実行**  
自動遷移には `set_realtime` ガードがあったが、左右キーの `begin_transition_to` には無く、cpal/FFI コールバック内で重い相関計算が走り得た。

→ **統合後: 解消。** `engine.rs` の `begin_transition_to` に同じガードが入り、worker 未着時は nominal entry。CHANGELOG にも記録あり。

### 3.3 P1（統合前から継続）

| 項目 | 内容 |
|---|---|
| CI | `push` / `PR` で走らない（`schedule` 12h と `tags` のみ） |
| キャッシュ書き込み | `cache::store` が `fs::write` 直書き。tmp+rename なし |
| content_hash | 先頭+末尾 64KiB + 長さのみ。中盤差し替えに弱い |
| ファイル肥大 | `main.rs` / `label_session.rs` / `engine.rs` / `analysis.rs` が 2500〜3300 行 |
| ミックスバス | peak ガード／ソフトクリップなし。f32 仕様だが live ではクリップし得る |
| メモリ | トラック全体を RAM 保持（後述の `docs/memory.md` で整理済み） |
| 依存監査 | `cargo audit` / `cargo deny` なし |

### 3.4 P2

- `cache_path` の hash 検証なし（`../` で cache 外へ書ける余地）
- CLI 本番が `funkot-core` を `features=["testutil"]` で必須依存
- `--highpass-hz` の `alias = "lpf-hz"`（意味が逆で事故のもと）
- 不正 JSON を黙殺（原因がログに残らない）
- FFI の同一 handle 並行呼び出し禁止が未文書化
- Docker の apt パッケージがバージョン未固定

### Baseline から見つかったテストの時間依存

Rust 1.98.1 / Linux、`RUST_TEST_THREADS=1 CARGO_PROFILE_RELEASE_LTO=false
cargo test --locked --workspace --release` でも
`render_transitions_only_is_shorter_than_full_mix` が0-frame出力で失敗した。
既定 `--jobs 1` のloader準備より10倍速renderが先に進み、遷移なしの待機経路へ入った。
これはシリアル実行だけで防げなかった。clip出力を目的とする2つのCLIテストを既存
`--jobs 2` に揃え、入力の事前準備を確定する。閾値、timeout、フェード、loader処理は変更しない。
streaming準備/nav/preview/枯渇自体の試験は `tests/engine.rs` に保持する。

### 検証結果（core 単独）

Linux / Rust 1.98.1、同じ合成入力・同じrelease設定（LTOのみCI同様無効）で確認した。
変更後 `RUST_TEST_THREADS=1 CARGO_PROFILE_RELEASE_LTO=false cargo test --locked
--workspace --release --no-fail-fast` は287件成功。表示上ignoreの1件は別process試験用helperで、
親テストが2プロセスを起動して実行している。実音源不在でearly-returnする既存試験は
実音源検証の合格には含めない。`work.sh --self-check`、README版数check、実gate8組合せ、
actionlint、cargo-deny 0.20.2 のadvisories/licenses/sourcesも成功。

既存 `synth_track(180/178 BPM, intro 8, main 8, outro 48, 44100Hz)` の2曲を
`--ci-fast --wav-format f32` と空cacheで前後それぞれレンダーした。WAV全体SHA-256は一致した。

| 出力rate | 変更前後で一致したWAV SHA-256 | sample peak | `|x|>1` samples | NaN/Inf |
|---|---|---:|---:|---:|
| 44100 | `679697042f5e8dfbd13be957194f07d55dd642cfe5bcc5e8837cf06ad6c76e7a` | 2.1944051 | 54393 | 0 |
| 48000 | `edae00b32fdea328c6d6a65cb94d3969ea689d656df41a5da62abfadf7268275` | 2.1622491 | 59406 | 0 |

peak超過は既存raw f32出力の観測であり、音を加工して解消していない。
cache の追加依存は tempfile 3.27.0 と必要な transitive 3件だけ。依存を総更新していない。
Windows既存entry置換は通常CI、Android core buildと製品実機受入は専用環境での未完条件。
ここにあるcore単独の成功をplayer統合、実音源の聴感、電源断耐性の合格に読み替えない。
